## Overview

Starting from chart version 0.16.0, Vault is **automatically initialised, unsealed, and
configured** during the first `helm install`. The previous three-step process is no longer
required for new installations:

**Before (manual, 3-step)**

```
# Step 1 — install chart with vault only
helm install --set backend.enabled=false ...

# Step 2 — run manual scripts
NAMESPACE=cycloid bash scripts/vault-init.sh
NAMESPACE=cycloid bash scripts/vault-config.sh

# Step 3 — full install
helm upgrade --set backend.enabled=true ...
```

**After (single command)**

```
helm install cycloid ./cycloid -f values.custom.yaml
```

The AppRole credentials (role IDs and secret IDs) for the `cycloid` and `cycloid-ro` roles are
generated by Helm at render time and stored in a Kubernetes Secret named
`<release>-vault-approle`. Vault is initialised and configured automatically via a `postStart`
lifecycle hook on the vault pod.

Backend pods that start before vault is ready will enter `CrashLoopBackOff` and recover
automatically once vault is configured — this is expected and requires no operator action.

## Fresh installation

### Prerequisites

- Kubernetes cluster with a default StorageClass (or an explicit `storageClass` configured)
- `kubectl` and `helm` (v3) installed locally
- `uuidgen` and `ssh-keygen` available on the operator's machine (for `generate-random-passwords.sh`)

### Step 1 — Generate passwords

`generate-random-passwords.sh` fills in all placeholder tokens in `values.custom.yaml`.
It does **not** generate vault AppRole credentials — those are now handled by Helm automatically.

```bash
export NAMESPACE=cycloid
cp values.sample.yaml values.custom.yaml
# Edit values.custom.yaml: set your domain, ingress, image tags, etc.
bash scripts/generate-random-passwords.sh
```

Secrets generated by this script:

| Placeholder | Description |
|---|---|
| `##backend-cryptoSigningKey##` | Backend crypto signing key |
| `##concourse-password##` | Concourse admin password |
| `##mysql-auth-rootPassword##` | MySQL root password |
| `##mysql-auth-password##` | MySQL application password |
| `##redis-auth-password##` | Redis password |
| `##concourse-postgresql-*##` | Concourse PostgreSQL passwords |
| `##concourse-web-encryption-key##` | Concourse web encryption key |
| `##backend-jwtKey1##` | JWT signing key |
| `##concourse-secrets-*Key##` | Concourse SSH keys (session, TSA host, worker) |

The following placeholders that existed in older chart versions are **no longer present** in
`values.sample.yaml` and do not need to be filled in:

- `##cycloid-vault-approle-role-id##`
- `##cycloid-vault-approle-secret-id##`
- `##cycloid-ro-vault-approle-role-id##`
- `##cycloid-ro-vault-approle-secret-id##`

### Step 2 — Install the chart

```bash
helm install cycloid ./cycloid \
  --namespace cycloid \
  --create-namespace \
  -f values.custom.yaml
```

There is no step 3. The vault init script runs automatically.

### What happens automatically

1. **Helm render time** — `vault-approle-secret.yaml` generates a Kubernetes Secret
   (`<release>-vault-approle`) containing four randomly generated credentials:
   `role-id`, `secret-id`, `role-id-ro`, `secret-id-ro`. These are stable across
   `helm upgrade` invocations because the template reads back the existing secret via
   Helm's `lookup` function.

2. **Pod start** — The vault pod mounts:
   - A 1 Mi PVC (`<release>-vault-init-data`) at `/vault/init-data`
   - A ConfigMap (`<release>-vault-init-script`) at `/vault/init-scripts`

3. **`postStart` hook** — `/vault/init-scripts/init.sh` runs inside the vault container and:
   - Waits for the vault listener to become ready
   - Initialises vault (`vault operator init -key-shares=5 -key-threshold=3`) and writes
     the output (5 unseal keys + root token) to `/vault/init-data/init.txt`
   - Unseals vault using keys 1–3 from `init.txt`
   - Enables the `approle` auth backend and the `cycloid` KV secrets backend
   - Writes the `cycloid` and `cycloid-ro` policies
   - Creates the `cycloid` and `cycloid-ro` AppRole roles and registers the pre-generated
     credentials from the `<release>-vault-approle` secret

4. **Backend pods** — Once vault is unsealed and the AppRole is configured, backend pods
   stop crashing and become healthy automatically.

## Vault init data storage options

Vault init data (`init.txt`) contains the unseal keys and the initial root token.
It must be persisted so that vault can be unsealed after a pod restart.

### Option A — PVC only (default, no RBAC required)

By default, init data is stored exclusively on a dedicated 1 Mi PVC named
`<release>-vault-init-data`. The vault pod is the only workload that mounts this PVC.

**No RBAC permissions are required beyond what the chart already requests.**

```yaml
# values.custom.yaml — nothing to configure; this is the default
vaultInitSecret:
  enabled: false
```

**Considerations**

- Init data is preserved across pod restarts and vault pod upgrades as long as the PVC exists.
- Deleting the PVC (e.g. during a full namespace wipe) means vault cannot be automatically
  unsealed. You will need to manually unseal vault or restore the PVC from a backup.
- The PVC uses `ReadWriteOnce` access mode and is 1 Mi in size.
- The `storageClassName` defaults to the class configured under
  `vault.server.dataStorage.storageClass` (which may be empty, meaning the cluster default
  is used).

### Option B — PVC + Kubernetes Secret (optional, requires RBAC)

When `vaultInitSecret.enabled=true`, the `postStart` script additionally writes the contents
of `init.txt` to a Kubernetes Secret via the cluster API after the vault configuration is
complete. This provides a second copy of the init data that is easier to back up through
standard Kubernetes tooling.

**Requirements**

- Your Kubernetes account must be allowed to create `Role` and `RoleBinding` resources in the
  target namespace. The chart deploys them automatically (`vault-init-secret-rbac.yaml`).
- The vault image must include `curl` and `base64` (standard in official `hashicorp/vault`
  Alpine images).

```yaml
# values.custom.yaml
vaultInitSecret:
  enabled: true
  secretName: cycloid-vault-init-keys   # name of the K8s Secret to create/update
```

The chart creates a `Role` limited to `get`, `create`, and `patch` on the specific secret
name, and binds it to the vault pod's service account (`<release>-vault`).

**What is stored in the secret**

```
kubectl get secret cycloid-vault-init-keys -o jsonpath='{.data.init\.txt}' | base64 -d
```

Output is the raw `vault operator init` text output:

```
Unseal Key 1: ...
Unseal Key 2: ...
Unseal Key 3: ...
Unseal Key 4: ...
Unseal Key 5: ...

Initial Root Token: hvs.XXXX
```

**Considerations**

- The secret is created with server-side apply (`fieldManager=vault-init`). Subsequent pod
  restarts will re-patch the secret if vault is reinitialised (e.g. after data loss).
- If the `curl` call fails (insufficient RBAC, network issue), the script logs a `WARNING`
  and continues — vault itself remains fully operational.
- Protect this secret carefully: it contains vault's root token and enough unseal keys to
  unseal vault.

## Vault backend storage options

Vault's own data (policies, auth backends, secrets engine state) must be persisted separately
from the init data.

### File backend (default)

Vault stores its data on a PVC managed by the `vault-helm` subchart
(`vault.server.dataStorage`). This is the default and requires no extra configuration.

```yaml
# values.custom.yaml (or leave at default)
vault:
  server:
    dataStorage:
      enabled: true
      size: 10Gi
      storageClass: ""   # use cluster default
```

The init data PVC (`<release>-vault-init-data`) is **separate** from this PVC and is always
created when `vault.enabled=true`, regardless of the backend type.

### MySQL / external backend

When using MySQL (or any external storage backend), you must disable vault's built-in data
PVC and configure the storage backend in `vault.server.ha.config` or
`vault.server.standalone.config`.

```yaml
vault:
  server:
    dataStorage:
      enabled: false   # no file-backend PVC
    standalone:
      config: |
        ui = true
        listener "tcp" {
          tls_disable = 1
          address     = "[::]:8200"
        }
        storage "mysql" {
          address  = "mysql-host:3306"
          username = "vault"
          password = "vaultpassword"
          database = "vault"
        }
```

The dedicated init data PVC (`<release>-vault-init-data`) is still created and mounted —
it stores only `init.txt` and is unaffected by `dataStorage.enabled=false`.

## Upgrading from a pre-auto-init installation

### What changes for existing users

**Nothing is required.** You can run `helm upgrade` with your existing `values.custom.yaml`
without any modifications. The chart is fully backward compatible.

- Existing AppRole credentials in `values.custom.yaml` (`backend.vault.roleId`,
  `backend.vault.secretId`) are used to seed the new `<release>-vault-approle` Secret on the
  first upgrade (via the fallback chain in `vault-approle-secret.yaml`). Subsequent upgrades
  preserve whatever is already in the secret via `lookup`.
- The `postStart` script includes an **upgrade guard**: if vault is already initialised but
  `init.txt` does not exist on the PVC (as is the case for all pre-auto-init installations),
  the script exits cleanly without touching vault. The vault pod starts normally.

### Warning: vault sealing after pod restart

On a pre-auto-init installation after upgrading the chart, **vault behaviour on pod restart
is unchanged from before the upgrade** — vault will be sealed and must be manually unsealed
using the existing `scripts/vault-unseal.sh` script.

The automatic unseal only activates once `init.txt` is present on the init data PVC
(see the next section).

### Optional: enable auto-unseal on an existing installation

If you want automatic unsealing going forward, seed `/vault/init-data/init.txt` on the PVC
with your existing vault init data.

**Format:** raw `vault operator init` text output — the same format produced by the
auto-init script and stored by `vault-init.sh` in `scripts/.out/vault-init.json`
(convert from JSON, or obtain from a previous `vault operator init` run):

```
Unseal Key 1: <key1>
Unseal Key 2: <key2>
Unseal Key 3: <key3>
Unseal Key 4: <key4>
Unseal Key 5: <key5>

Initial Root Token: hvs.XXXX
```

To write the file into the running vault pod:

```bash
# Copy your existing init data (plaintext) into the pod
kubectl -n cycloid cp /path/to/init.txt cycloid-vault-0:/vault/init-data/init.txt
```

From the next pod restart onward, the `postStart` script will detect `init.txt`,
unseal vault automatically, and re-configure the AppRole (idempotent — safe to run
on an already-configured vault).

> **Note:** The script re-applies the AppRole role-id and secret-id values every time.
> These must match the credentials currently registered in vault or vault authentication
> will break. If in doubt, do not seed `init.txt` and continue using manual unsealing.

### Optional: migrate read-only approle credentials

If your pre-auto-init `values.custom.yaml` contained placeholder patterns
`##cycloid-ro-vault-approle-role-id##` / `##cycloid-ro-vault-approle-secret-id##` that were
**never replaced** (i.e. the Concourse vault sidecar was not functional), you do not need to
do anything — fresh credentials are generated by Helm automatically.

If the read-only approle was previously configured and you want to preserve the existing
credentials (to avoid re-configuring Concourse pipelines that reference them), pass the
existing values via `vaultMigration`:

```yaml
# values.custom.yaml — one-time migration, safe to remove after first upgrade
vaultMigration:
  roRoleId:   "<existing cycloid-ro role-id>"
  roSecretId: "<existing cycloid-ro secret-id>"
```

These values are used as a fallback seed during the upgrade (after checking the existing
secret via `lookup`). They are ignored on subsequent upgrades once the secret exists.
You can remove them from `values.custom.yaml` after the first successful `helm upgrade`.

Read-write credentials (`backend.vault.roleId` / `backend.vault.secretId`) follow the same
fallback pattern but are read from the existing `backend.*` keys that were already present
in `values.custom.yaml`.

## Design space: approaches considered

This section documents all approaches evaluated for solving the vault bootstrap problem,
the constraints each one ran into, and why the current solution was chosen.

### The bootstrap problem

Vault must be initialised and an AppRole configured before the Cycloid backend can start.
The backend needs the AppRole `role-id` and `secret-id` at startup. These values are not
known until vault is initialised — creating a chicken-and-egg dependency that the original
3-step manual process solved by serialising the steps by hand.

The constraints for any automated solution were:

- No extra Docker images (only vault's own container and whatever is already in the chart)
- No Bitnami images
- The deploying K8s account may **not** be allowed to create `Role` or `RoleBinding`
- The solution must not break existing `helm upgrade` workflows
- MySQL as vault backend (`dataStorage.enabled: false`) must be supported

---

### A — Helm post-install hook Job

A Kubernetes `Job` runs after `helm install` completes, `exec`s into the vault pod, and
performs init + AppRole configuration, then writes the credentials to a K8s Secret that the
backend pods read.

| | |
|---|---|
| **Pros** | Clean lifecycle: the Job is a first-class K8s resource, its completion is observable, it can retry on failure, and logs are easy to inspect. Credentials can be distributed to other pods via a proper Secret without CrashLoopBackOff. |
| **Cons** | The Job pod needs an image with `kubectl` or the vault CLI plus Kubernetes API access. Using `kubectl` requires either bundling `kubectl` in a custom image or using a bitnami utility image — both rejected. Using the vault CLI requires a `ClusterRole` or `Role` + `ServiceAccount` + `RoleBinding` for `exec` permissions, which the deploying account may not be able to create. The Job also needs `get/create/patch` on Secrets. Helm hooks do not participate in `helm upgrade` diff so the hook can silently re-run. |
| **Verdict** | Blocked by RBAC restriction and extra-image restriction for operators with limited permissions. Viable for operators with full K8s access — see [Alternative: breaking-change redesign](#alternative-breaking-change-redesign-for-users-with-full-k8s-access). |

---

### B — Init container on the vault pod

An init container runs before the vault container starts, waits for vault readiness (it
can't — vault isn't running yet), or a sidecar container runs alongside vault and waits
for it.

| | |
|---|---|
| **Pros** | Init containers have a well-defined completion contract; their logs are always available. A properly ordered init container could run after vault is started via a different mechanism. |
| **Cons** | An init container cannot wait for vault to be ready because vault hasn't started yet — init containers must complete before the main container starts. A sidecar would need to be added to the vault StatefulSet via the vault-helm subchart's `extraContainers`, requires its own image (vault, vault-cli, or custom), and shares the same RBAC issues if it needs to write K8s Secrets. Process-namespace sharing (`shareProcessNamespace: true`) would let a sidecar call `vault` via the main container's filesystem but adds complexity. |
| **Verdict** | Sidecar variant is workable but adds image complexity. The `postStart` hook on the vault container itself is simpler and uses no extra images. |

---

### C — postStart hook on the vault pod (implemented)

The vault container's `postStart` lifecycle hook runs a shell script that performs the full
init, unseal, and AppRole configuration using only the vault CLI already present in the
`hashicorp/vault` image.

| | |
|---|---|
| **Pros** | Zero extra images. No RBAC needed by default (init data goes to a PVC). Works with MySQL backend. Fully idempotent. No Helm hook ordering issues. |
| **Cons** | `postStart` is not guaranteed to run before the container is marked `Running` — Kubernetes does not wait for `postStart` to complete before registering the pod as ready (though in practice it runs immediately). The hook's stdout/stderr is not directly captured in pod logs; failures manifest as the container entering `Error` state. Backend pods will `CrashLoopBackOff` until vault is ready (acceptable per requirements). The vault pod itself is blocked from receiving traffic until `postStart` completes, which is actually desirable here. |
| **Verdict** | Chosen. Meets all constraints. CrashLoopBackOff on backend pods is acceptable. |

**Storing the init data — sub-options evaluated within this approach:**

| Sub-option | RBAC needed | Survives namespace wipe | Notes |
|---|---|---|---|
| Write to vault's own data PVC | None | Yes (same PVC) | Not possible when `dataStorage.enabled: false` (MySQL backend) |
| Dedicated 1 Mi PVC (implemented, default) | None | Yes (separate PVC) | Works with all backend types. Operator must back up or preserve PVC. |
| Write to K8s Secret via API (implemented, optional) | `Role` + `RoleBinding` | Yes (K8s Secret) | Requires deploying account to be able to create Role/RoleBinding. Optional feature. |
| Write to external secret manager (Vault, AWS SSM…) | Varies | Yes | Out of scope; would require additional configuration and credentials at init time. |

---

### D — Cloud KMS / Transit auto-unseal

HashiCorp Vault supports delegating the unseal operation to an external KMS
(AWS KMS, GCP Cloud KMS, Azure Key Vault) or to a second Vault instance (Transit auto-unseal).
With this mechanism vault unseals itself automatically on startup — no unseal keys need to be
stored or managed by the chart.

| | |
|---|---|
| **Pros** | Strongest security model: unseal keys never touch the filesystem or a K8s Secret. Vault restarts are fully automatic. Root token can be revoked after initial setup. |
| **Cons** | Requires a cloud account, pre-provisioned KMS key, and credentials available to the vault pod (via IRSA, Workload Identity, or a K8s Secret). Not suitable for air-gapped or on-premises deployments without a cloud provider or a second Vault instance. Significant configuration overhead for operators. |
| **Verdict** | Out of scope for the default on-premises chart. Operators who have access to a cloud KMS should configure `vault.server.standalone.config` (or HA config) with the appropriate `seal` stanza directly — the chart does not obstruct this. The `postStart` script detects an already-initialised vault and exits without interfering. |

### Credential pre-generation approaches

The vault AppRole `role-id` and `secret-id` must be known to both vault (to configure the
AppRole) and to the backend pods (to authenticate). Several approaches were considered for
distributing these values:

| Approach | Notes |
|---|---|
| Static values in `values.custom.yaml` | Original approach. Requires manual generation (old `vault-config.sh`). Values are committed to configuration files. |
| Generate in Helm, pass via `extraEnvironmentVars` | `vault-helm`'s `extraEnvironmentVars` only accepts `{KEY: string_value}` — attempting to use `valueFrom.secretKeyRef` renders as a literal string. Not viable. |
| Generate in Helm, pass via `extraSecretEnvironmentVars` | `vault-helm`'s purpose-built mechanism for secret-backed env vars. Accepts `{envName, secretName, secretKey}`. **Used in the implementation.** |
| Generate in Helm hook, write to Secret, mount in vault pod | Requires extra image or kubectl; see option A above. |
| Generate in vault pod, write to shared ConfigMap | ConfigMaps are not designed for secrets. Requires RBAC write access. |
| Generate in Helm, store in dedicated Secret, reference everywhere | **Implemented.** `vault-approle-secret.yaml` renders credentials once using Sprig `uuidv4`/`randAlphaNum`, stabilised across upgrades via `lookup`. All backend templates reference this secret directly through the `backend.vaultEnvVars` helper. |

## Technical implementation details

### AppRole credential pre-generation

`templates/vault-approle-secret.yaml` generates a `Secret` containing four fields:
`role-id`, `secret-id`, `role-id-ro`, `secret-id-ro`.

Each field follows a three-level fallback chain evaluated at Helm render time:

```
1. Existing secret (helm upgrade — lookup returns current value, preserving it)
2. Seed value from values.yaml (migration path for upgrade from pre-auto-init)
3. Freshly generated random value (new install)
```

In template form:

```
{{ if $existing }}
  {{ index $existing.data "role-id" | b64dec | quote }}
{{ else if .Values.backend.vault.roleId }}
  {{ .Values.backend.vault.roleId | quote }}
{{ else }}
  {{ uuidv4 | quote }}
{{ end }}
```

`uuidv4` is used for role IDs (UUID format required by vault) and `randAlphaNum 32` for
secret IDs (arbitrary alphanumeric string).

The Helm `lookup` function queries the live cluster at render time. On first `helm install`
it returns `nil` (secret does not exist yet) so the generated random values are used. On
`helm upgrade` it returns the existing secret so values are preserved unchanged.

**Key consequence:** `helm template` (offline rendering) always generates new random values
because `lookup` returns `nil` without cluster access. Use `helm upgrade --dry-run` to
preview what an upgrade would actually apply.

### Init script lifecycle

The full init script is defined as a Helm named template (`cycloid.vaultInitScript` in
`templates/_helpers.tpl`) and rendered into `templates/vault-init-configmap.yaml` at deploy
time. Helm conditionals (e.g. the `vaultInitSecret.enabled` block) are resolved at render
time, so the ConfigMap contains a static shell script with no Helm syntax.

The script runs inside the vault container via `postStart`:

```
vault pod starts
  → postStart: /bin/sh /vault/init-scripts/init.sh
      → wait for vault listener (until vault status)
      → upgrade guard check
      → vault operator init (if not initialised)
      → vault operator unseal ×3 (if sealed)
      → vault login (root token from init.txt)
      → vault auth enable approle
      → vault secrets enable -path cycloid kv
      → vault policy write cycloid-ro
      → vault policy write cycloid
      → vault write auth/approle/role/cycloid (role-id + secret-id)
      → vault write auth/approle/role/cycloid-ro (role-id-ro + secret-id-ro)
      → [optional] curl K8s API to write init.txt to Secret
```

Output parsing uses only POSIX tools available in the vault Alpine image (`grep`, `awk`,
`sed`) — `jq` is not available and is not required:

```sh
# Extract unseal key N from text output
grep "Unseal Key [1-3]:" "$INIT_DATA" | awk '{print $NF}'

# Extract root token
grep "Initial Root Token:" "$INIT_DATA" | awk '{print $NF}'
```

All configuration steps are idempotent: each command is guarded by a prior `vault read`
or `vault list` check, so restarting the vault pod after a partial initialisation is safe.

**The vault pod is the only actor that writes to `/vault/init-data/init.txt`.** No other
pod or sidecar mounts the init-data PVC.

### Upgrade guard

The guard near the top of the init script handles the transition from a pre-auto-init
installation where vault is already initialised but no `init.txt` exists on the new PVC:

```sh
if vault status 2>/dev/null | grep -q "Initialized.*true" && [ ! -f "$INIT_DATA" ]; then
  echo "INFO: Vault already initialised but no init data found on PVC."
  echo "INFO: Skipping auto-configuration. Seed $INIT_DATA to enable auto-unseal."
  exit 0
fi
```

This means the `postStart` script is safe to deploy on an existing installation: it exits
without touching vault in any way. The vault pod starts normally and existing manual unseal
procedures continue to work.

Once an operator seeds `init.txt` (by copying it into the pod), the guard no longer fires
and the script takes over unseal and reconfiguration from the next restart.

### Unified vault env-var helper

Before this change, every backend template (deployment, task manager, 5 cronjobs) had its
own copy of the vault env-var block reading from two different secrets depending on whether
`vault.enabled` was true or false, with some templates referencing keys that were removed
from `backend-secret.yaml`.

The `backend.vaultEnvVars` helper in `_helpers.tpl` is now the single source of truth:

```
{{- define "backend.vaultEnvVars" -}}
- name: "VAULT_URL"
  value: {{ .Values.backend.vault.url | quote }}
- name: "VAULT_ROLE_ID"
  valueFrom:
    secretKeyRef:
      name: {{ if .Values.vault.enabled }}
               {{ include "cycloid.vaultApproleSecretName" . }}
             {{ else }}
               {{ template "backend.backendSecretName" . }}
             {{ end }}
      key: {{ if .Values.vault.enabled }}role-id{{ else }}vault-role-id{{ end }}
- name: "VAULT_SECRET_ID"
  ...
{{- end -}}
```

When `vault.enabled=true`:
- `VAULT_ROLE_ID` and `VAULT_SECRET_ID` come from `<release>-vault-approle` (keys `role-id` / `secret-id`)

When `vault.enabled=false` (external vault):
- `VAULT_ROLE_ID` and `VAULT_SECRET_ID` come from `<release>-backend` (keys `vault-role-id` / `vault-secret-id`)

All seven backend templates call `{{- include "backend.vaultEnvVars" . | nindent N }}`.

## Potential improvements

### 1. Cloud KMS / Transit auto-unseal

For production deployments with cloud access, replacing Shamir key unsealing with a cloud
KMS eliminates the need for `init.txt` entirely. Vault unseals itself using a KMS key that
it holds no local copy of. The init data PVC, the upgrade guard, and the secret backup
feature all become unnecessary.

This can already be configured today by setting the appropriate `seal` stanza in
`vault.server.standalone.config`. The init script exits cleanly for an already-initialised
vault, so no chart changes are needed.

### 2. Replace postStart with a proper init mechanism

`postStart` has a subtle contract: Kubernetes does not guarantee it runs before the
container is marked ready, and its exit code is not surfaced cleanly in pod status.
A more robust mechanism would be:

- A **sidecar container** that shares the vault process namespace (`shareProcessNamespace:
  true`) so it can call `/vault/init-scripts/init.sh` after detecting vault is up, then
  sleep forever. Kubernetes 1.29+ supports `restartPolicy: Never` on individual sidecar
  containers, which would allow it to exit cleanly after one successful run.
- An **external controller** (see improvement 4) that handles the full lifecycle
  declaratively.

The main obstacle is that a sidecar still needs the vault CLI, which is available by
sharing the process namespace with the vault container's binary at
`/vault/bin/vault` — no extra image needed.

### 3. Structured init.txt (JSON)

The current `init.txt` uses vault's human-readable text output format, parsed with `grep`
and `awk`. The script could instead pass `-format=json` to `vault operator init` and parse
with `jq` — but `jq` is not installed in the vault Alpine image.

A better structured alternative would be to store each unseal key in a separate file (or as
separate keys in the K8s Secret), making individual key rotation and deletion easier:

```
/vault/init-data/unseal-key-1
/vault/init-data/unseal-key-2
/vault/init-data/unseal-key-3
/vault/init-data/root-token
```

This would also allow deleting the root token file after initial configuration as a security
hardening measure, while keeping the unseal keys for restart automation.

### 4. Vault Operator / Bank Vaults

[Bank Vaults](https://bank-vaults.dev/) (open source, formerly Banzai Cloud) provides a
Kubernetes operator that manages vault initialisation, unsealing, and configuration
declaratively via a `Vault` CRD. It is the most complete solution for long-lived production
vault deployments on Kubernetes.

The current approach could be replaced by including Bank Vaults as an optional dependency,
activated via a `vaultOperator.enabled` flag. The Bank Vaults operator supports:
- Multiple unseal mechanisms (K8s Secrets, cloud KMS, HSM)
- CRD-based vault policy and auth configuration
- Automatic secret injection via mutating webhooks

This would be a **breaking change** for operators who have customised vault via the current
`postStart` mechanism.

### 5. Remove CrashLoopBackOff on backend pods

Backend pods currently crash-loop while vault is being initialised because they try to
authenticate to vault before the AppRole is configured. Three approaches exist to eliminate
this:

**a) Helm hook ordering** — A `pre-install` or `post-install` hook Job that signals
readiness (e.g. creates a ConfigMap or updates a Secret) before backend pods are created.
Backend pods could use an init container that waits for this signal. Requires RBAC.

**b) Vault agent injector** — The Vault Agent Injector sidecar handles authentication and
secret injection transparently. Backend pods would not need to know the AppRole credentials
at startup — the sidecar handles token renewal. This is a significant architecture change
and introduces the injector as a dependency.

**c) Backend startup retry logic** — The backend application itself could implement a retry
loop with exponential backoff on vault authentication failure, converting the
`CrashLoopBackOff` into a graceful wait. This is an application-level change.

## Alternative: breaking-change redesign for users with full K8s access

The current implementation deliberately avoids `Role`, `RoleBinding`, and any RBAC-intensive
patterns (except for the optional `vaultInitSecret` feature) because a subset of operators
cannot create these resources. If your deployment environment **has** full K8s RBAC access
and you are not constrained by the backward-compatibility requirement, a cleaner design is
possible with a breaking change.

### What the breaking-change design looks like

```
helm install cycloid ./cycloid -f values.custom.yaml
                    │
        ┌───────────┼──────────────────────────────────────┐
        │           │                                      │
  Helm hook:  Vault pod              Backend / concourse pods
  pre-install   starts                 WAIT on init Job
  Job (vault   normally,                  completion
  image)       no postStart               signal
        │
        │  1. vault operator init
        │  2. vault operator unseal
        │  3. vault auth enable approle
        │  4. vault policy write ...
        │  5. vault write approle/role/cycloid
        │  6. kubectl patch secret <release>-vault-approle
        │     with real role-id/secret-id from vault
        │  7. kubectl create configmap vault-ready
        └──────────────────────────────────────────────────
                              │
                  Backend init container:
                  wait for configmap vault-ready
                  → backend starts
```

**Differences from the current approach**

| Aspect | Current (postStart, no RBAC) | Breaking-change (hook Job) |
|---|---|---|
| K8s RBAC required | None (default) or Role+RoleBinding (optional) | Role + RoleBinding mandatory |
| Extra image | None | None (uses vault image via `image:` in Job spec) |
| CrashLoopBackOff on backend | Yes, until vault is ready | No — backend waits on Job completion signal |
| Credential flow | Pre-generated by Helm, registered by postStart | Generated by vault, written back to K8s Secret by Job |
| Credential stability | Preserved by `lookup` across upgrades | Preserved by `lookup` across upgrades |
| Observability | `kubectl logs cycloid-vault-0` (postStart mixed with vault logs) | `kubectl logs job/cycloid-vault-init` (dedicated log stream) |
| Breaking change | No (backward compatible) | Yes (requires RBAC, changes credential flow) |
| MySQL backend | Supported (dedicated PVC) | Supported |
| Upgrade on existing install | Upgrade guard exits cleanly | Hook re-runs; must be idempotent and detect existing vault |

**Minimum RBAC the Job needs**

```yaml
rules:
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["create"]
    resourceNames: ["<release>-vault-0"]
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["get", "patch"]
    resourceNames: ["<release>-vault-approle"]
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["create"]
    resourceNames: ["<release>-vault-ready"]
```

**When to choose the breaking-change design**

- Your K8s deployment account can create `Role` and `RoleBinding`
- You need a cleaner operational model (no CrashLoopBackOff, dedicated job logs)
- You are doing a new installation (no upgrade path needed)
- You want to revoke the root token after installation and the Job can do that as its
  final step

**When to stay with the current design**

- Your K8s account cannot create `Role` or `RoleBinding`
- You are upgrading an existing installation
- You want the simplest possible configuration (single values file, no RBAC planning)
- You are in an air-gapped environment with minimal cluster privileges

## Values reference

New values introduced by the auto-init feature:

| Value | Default | Description |
|---|---|---|
| `vaultInitSecret.enabled` | `false` | Write init data to a K8s Secret in addition to the PVC. Requires RBAC (Role + RoleBinding created automatically). |
| `vaultInitSecret.secretName` | `cycloid-vault-init-keys` | Name of the K8s Secret to create/update with vault init data. |
| `vaultMigration.roRoleId` | `""` | One-time seed for the `cycloid-ro` AppRole role-id on upgrade. Ignored once the approle secret exists. |
| `vaultMigration.roSecretId` | `""` | One-time seed for the `cycloid-ro` AppRole secret-id on upgrade. Ignored once the approle secret exists. |

Values that are **no longer required** in `values.custom.yaml` for new installations:

| Value | Previous purpose |
|---|---|
| `backend.vault.roleId` | AppRole role-id (now auto-generated). Still used as migration seed if set. |
| `backend.vault.secretId` | AppRole secret-id (now auto-generated). Still used as migration seed if set. |

Kubernetes resources created by the auto-init feature:

| Resource | Kind | Condition |
|---|---|---|
| `<release>-vault-approle` | Secret | `vault.enabled=true` |
| `<release>-vault-init-data` | PersistentVolumeClaim | `vault.enabled=true` |
| `<release>-vault-init-script` | ConfigMap | `vault.enabled=true` |
| `<release>-vault-init-secret` | Role + RoleBinding | `vault.enabled=true` AND `vaultInitSecret.enabled=true` |
